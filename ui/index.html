IntentGuard

Rain controls whether an agent can spend. IntentGuard verifies whether the spend matches what the user asked for.

Every result on this page is captured verbatim from one real cargo run — live Claude API calls, real Rain sandbox transactions, and audit records written to Monad testnet. Nothing here is mocked.

The gap

Rain's Agent Control Layer enforces limits on the payment: merchant category, amount, frequency, timing, active cards. Every one of those is a property of the transaction. None is a property of the task. An agent told "get me to NYC for under $500" that books a $450 flight to Miami passes every control Rain has — right MCC, right amount, first attempt of the day. IntentGuard sits one layer above the money and checks the one thing the payment rails structurally cannot see.

The task is what the user actually said: destination, max_budget, purpose, and the travel window start_date–end_date. Three of those are enforced against every proposed action. Dates are structured fields rather than prose inside the booking description for one reason: a date buried in free text can be displayed but not validated, so an agent booking days the user never asked to pay for would sail straight through.

The no-fabrication guard

A vague request is an error to report, not a gap to fill in

parse_task_from_prompt has no fallback, on purpose. Inventing a destination, a budget, or a travel date the user never gave would fabricate the exact intent this project exists to check. The guard is enforced twice: the model is instructed to return {"error": ...} when a field is missing, and the parser independently rejects an empty destination, a non-finite or non-positive budget, an empty purpose, and any date that is not a full YYYY-MM-DD — in case a model answers in the right shape with nothing in it.

Dates get held to that standard strictly: a month and a day with no year is incomplete. "August 15th" does not say which August, and picking the nearest one is a guess about what the user meant. That is why the example request states the year outright — the parser will not supply one, so an interactive request has to carry it.

This is the designed behavior, not a failure. No task invented, no agent invoked, no Rain call, no money path opened. The system refuses to guess what you meant.

The compile-time guarantee

Not tested against — structurally impossible

Every other safety property here is a runtime check. This one is not. ApprovedAction wraps a &ProposedAction in a field private to intent_check, so the only code in the program that can construct one is evaluate, on the branch where it returns Verdict::Approved. Rain's entry point takes that type and nothing else.

1 — The token type · src/intent_check.rs
pub struct ApprovedAction<'a>(&'a ProposedAction);   // field is private to this module
2 — The payment entry point · src/rain_client.rs
pub async fn execute_rain_flow(
    approved: &ApprovedAction<'_>,   // not &ProposedAction
    config: &RainConfig,
    mcc: &str,
    settlement: Settlement,
) -> Result<RainResult, Error>

Calling Rain on a blocked or escalated action is not a bug that code review has to catch. There is no value of the right type to pass, so the program does not build. The denied branch in main.rs holds no token and therefore has no reachable path to the payment layer.

Verified from chain, not from memory

At the end of the run, IntentGuard reads one of its own records back off Monad testnet — through the RPC, not from the program's own variables. Only the hash goes on chain, never the task: destination, budget, purpose, and travel dates are exactly the private context that makes IntentGuard work, and publishing them would defeat the point. Anyone holding the original task can recompute the digest and prove it matches; the chain alone reveals nothing.
